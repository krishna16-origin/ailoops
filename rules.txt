Use the uploaded 130 SKILL.md files as the design + implementation reference when generating or modifying code.

1. Core coding behavior
First understand the existing project before editing.
Inspect the relevant files, architecture, components, dependencies, and existing styles.
Do not rewrite unrelated code.
Preserve existing functionality unless the task explicitly requires changing it.
Reuse the project's existing patterns before introducing a new framework/library.
Keep implementation modular and readable.
Avoid unnecessary dependencies.
Never fake functionality with static UI when the requested feature is supposed to work.
Handle loading, error, empty, disabled, and success states.
Consider responsive behavior from the beginning.
Clean up event listeners, animation loops, observers, WebGL contexts, and resources when components are removed.
Prefer progressive enhancement: the experience should remain usable if advanced effects fail.
Keep visual effects separate from application logic.
Before coding
Identify the requested outcome.
Identify constraints.
Inspect the current implementation.
Find the authoritative source of truth.
Decide the minimum files that actually need modification.
Implement.
Test the real user path.
Inspect the final result visually where applicable.
Fix discovered issues.
Verify again.

Never claim something was tested or verified if it was only inferred.

Do not mix several visual languages unless the combination is intentional.

Do not default to the same visual language every time. Before picking one, briefly consider at least 2-3 candidates from the list above that could fit the purpose/audience, and choose deliberately based on the project's content, industry, and tone rather than habit. If the last few builds in this conversation used "dark glass" or "clean SaaS," actively favor a different direction unless the user's brand or request specifically calls for continuity.

4. Layout system

Use strong composition rather than simply stacking cards.

Consider:

asymmetric grids
split layouts
framed containers
nested containers
editorial grids
technical information layouts
full-bleed sections
oversized typography
controlled whitespace
visual anchors
deliberate section transitions

Use consistent:

max-width
gutters

grid columns
typography scale
border treatment
corner treatment

If using a technical aesthetic, thin lines, corner brackets, frames, grids, and small metadata can create structure without adding unnecessary decoration.

5. Typography

Typography should establish hierarchy.

Use:

clear display type for major statements
readable body text
restrained metadata
deliberate line lengths
strong contrast between heading/body/supporting text

Do not use huge typography simply because it looks impressive.

Typography should communicate the product/story.

6. Color system

Define colors as tokens instead of scattering arbitrary values throughout the code.

Then use those tokens consistently.

Accent colors should communicate hierarchy or state, not decorate every element.

Do not default to the same palette on every build. Never reach for blue/purple gradients, teal-on-navy, or indigo/violet accents as the automatic default — these are the most overused "AI-generated" combinations. Before choosing colors, pick a palette strategy deliberately based on the project, for example:

monochromatic (one hue, varied in lightness/saturation)
analogous (neighboring hues)
complementary or split-complementary
triadic
warm neutral / earthy (clay, sand, olive, rust)
cool neutral / muted (stone, sage, slate)
jewel tones (emerald, amber, burgundy, deep teal)
duotone (two strong colors, minimal middle ground)
high-contrast mono + single accent (black/white/off-white + one deliberate accent)
saturated/vibrant (when the brand calls for energy)
pastel/soft (when the brand calls for approachability)

Derive the palette from the product's purpose, industry, and audience, not from habit. A fintech dashboard, a children's app, a fashion brand, and a developer tool should not converge on the same colors.

Within a single conversation, actively vary the palette strategy across different builds/projects. If a prior build in this session used a dark-navy-plus-purple system, the next unrelated build should not reuse that same hue family or gradient direction unless the user is iterating on the same project or explicitly asked to match existing branding.

Always define at least: a background scale (2-3 steps), a text scale (primary/secondary/muted), one or two accent colors tied to specific meaning (primary action, success, warning, error), and border/divider colors — as tokens, not ad hoc hex codes sprinkled through markup.

Avoid faded, washed-out, low-saturation palettes as the default. Unless the brand/content explicitly calls for a soft, pastel, or muted mood, prefer confident, saturated color: rich jewel tones, punchy brights, deep saturated darks, bold high-contrast combinations. Build multi-color systems rather than one washed-out hue doing all the work — typically a primary, a secondary, and one or two supporting accents that are visibly distinct from each other, not just tints/shades of the same dull gray-blue.

Quick self-check: if every color in the palette could pass for "off-white," "light gray," or "dusty blue-gray," the palette is too faded — increase saturation and contrast before finalizing.

7. Glass UI

When glass is appropriate:

use transparency carefully
use subtle borders
use backdrop blur
use controlled highlights
maintain strong text contrast
avoid making every element glass

Preferred structure:

.glass {
  background: rgba(255,255,255,.055);
  border: 1px solid rgba(255,255,255,.12);
  backdrop-filter: blur(20px);
  -webkit-backdrop-filter: blur(20px);
}

Glass should create depth, not reduce readability.

8. Shadows

Shadows should establish hierarchy.

Use:

small shadow → subtle separation
medium shadow → elevated component
large shadow → major floating element

Avoid giving every card a giant shadow.

9. Borders and gradients

Use border gradients, masks, and glow effects only where they strengthen hierarchy.

Good uses:

active states
important containers
hero objects
focused controls
futuristic technical framing

Bad use:

putting glowing borders around everything.

restrained + intentional + physical + responsive

Prefer:

enter → establish → interact → transition

rather than:

11. GSAP / ScrollTrigger

Use GSAP when choreography needs to be precise.

Good use cases:

hero entrance
staggered text
pinned sections
scroll-scrubbed storytelling
masked reveals
timeline sequences
controlled parallax

Example architecture:

const tl = gsap.timeline();

tl.from(".hero-title", {
  y: 60,
  opacity: 0,
  duration: 0.8,
  ease: "power3.out"
})
.from(".hero-meta", {
  y: 20,
  opacity: 0,
  duration: 0.5
}, "-=.4");

For scroll:

gsap.to(".visual", {
  scale: 1.15,
  scrollTrigger: {
    trigger: ".section",
    start: "top bottom",
    end: "bottom top",
    scrub: true
  }
});

Always clean up ScrollTriggers in component-based applications.

12. Lenis / smooth scrolling

Use smooth scrolling only when it improves the experience.

It should support:

cinematic storytelling
controlled transitions
scroll-driven animation

It should not make a normal utility page feel artificially slow.

13. IntersectionObserver

For simple reveal animations, prefer native browser APIs over GSAP.

const observer = new IntersectionObserver((entries) => {
  entries.forEach(entry => {
    if (entry.isIntersecting) {
      entry.target.classList.add("is-visible");
      observer.unobserve(entry.target);
    }
  });
});

Use GSAP when the animation needs choreography; use IntersectionObserver when a simple trigger is enough.

14. WebGL / Three.js

When 3D is requested, use Three.js/WebGL intentionally.

Architecture:

Scene
 ├── Camera
 ├── Renderer
 ├── Lights
 ├── Objects
 ├── Materials
 ├── Animation loop
 └── Resize handling

Do not add Three.js merely because "3D looks cool."

Choose the appropriate lane:

Lane A — subtle depth

For normal product/landing pages.

Lane B — data/particle intelligence

For technical/AI experiences.

Lane C — 3D product object

When the product itself benefits from spatial presentation.

Lane D — cinematic world

For immersive brand experiences.

Keep the WebGL layer visually integrated with the DOM.

15. WebGL performance

Always consider:

device pixel ratio
geometry complexity
particle count
shader complexity
draw calls
texture size
animation frequency
mobile GPU limitations

Use:

renderer.setPixelRatio(
  Math.min(window.devicePixelRatio, 2)
);

Do not perform unnecessary work when the canvas is invisible.

Pause or reduce expensive simulation when appropriate.

16. Particles

For particle systems:

reuse buffers
avoid allocating objects every frame
use typed arrays where appropriate
use GPU shaders for large particle systems
recycle particles
emit based on distance when creating trails
avoid time-based particle spawning when spatial consistency is required

Do not create thousands of DOM elements for particle effects.

17. Cursor effects

For cursor trails/ripples:

track pointer movement
interpolate toward the target
avoid directly snapping
use a bounded/recycled particle pool
keep effects screen-space when they are meant to follow the cursor
remove/disable on touch devices when appropriate

Cursor effects should enhance interaction rather than interfere with controls.

18. Mouse-driven 3D/orbit

Use damped motion.

Conceptually:

current.x += (target.x - current.x) * 0.08;
current.y += (target.y - current.y) * 0.08;

Separate:

pointer intent
camera movement
object movement
parallax

Do not directly bind every pixel of mouse movement to a large visual transformation.

19. Reduced motion

Respect:

@media (prefers-reduced-motion: reduce) {
  * {
    animation-duration: 0.001ms !important;
    animation-iteration-count: 1 !important;
    scroll-behavior: auto !important;
  }
}

For JS/WebGL, also explicitly check:

const reducedMotion =
  window.matchMedia("(prefers-reduced-motion: reduce)").matches;

Then reduce or disable expensive motion.

31. Variation & anti-repetition rule

Treat every new build (a new project, or an unrelated feature within the same project) as a fresh creative decision, not a template to reuse from the last output.

Before generating, briefly decide and vary, on purpose, across builds:

art direction (see section 3 — do not repeat the last one used)
color palette strategy (see section 6 — do not repeat the last hue family/gradient)
layout composition (asymmetric grid vs. split vs. framed vs. editorial vs. full-bleed — do not default to the same one)
typography pairing (do not always reach for the same display/body combination)
corner and border treatment (sharp vs. soft vs. mixed — do not default to rounded-everything)

Exceptions — do NOT vary for the sake of varying when:

the user is iterating on/continuing the same project (match existing tokens, direction, and components)
the user gives explicit brand guidelines, a reference, or existing design system to follow
the user explicitly asks to reuse a previous style

When in doubt about whether a request is a continuation or a new project, prefer continuity within the same file/codebase and prefer variation across clearly separate/unrelated requests.

The goal is that two different builds produced in this tool should not visually look like they came from the same template with the text swapped out.

32. Awwwards-tier design bar

When the user asks to build something that stands out, or references "awwwards," "award-winning," "best in class," "top tier," or similar, raise the craft bar above the general baseline in sections 3-31:

Study the visual grammar of Awwwards/FWA/CSSDA-tier sites (via the reference skills where available): a strong single point of view per project, oversized confident typography, deliberately chosen imagery, layered depth, considered micro-interactions, and one or two clear "hero moments" the page is built around — not twenty competing effects.

Include at least one deliberate signature detail per build, appropriate to the product: a custom cursor, an unusual navigation pattern, a distinctive page transition, a textured/grain layer, an unexpected scroll behavior, or a bold color moment. Award-tier work is remembered for one or two specific craft decisions, not generic polish everywhere.

Push color further than a "safe" SaaS palette — use multiple confident colors together (not just one hue plus neutrals), strong contrast, and deliberate color blocking, while still keeping text contrast accessible (see section 27).

Push typography — mix a distinctive display treatment (unusual weight, spacing, size, or typeface pairing) with a clean, restrained body face. Scale should feel intentional and specific to this project, not a generic "big header, medium subhead, small body" default.

Motion should feel premium: eased, staged, and choreographed (see sections 10-11) — not default browser transitions or effects added for their own sake.

Do not sacrifice usability, performance, or accessibility for spectacle. The best award-tier sites are fast and functional as well as visually bold — the craft is in balancing both, not choosing one over the other.
